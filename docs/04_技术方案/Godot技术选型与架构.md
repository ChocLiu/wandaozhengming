# Godot 技术选型与架构

> 状态：初稿 v0.1 · 2026-08-30
> 本系统服务的核心命题：**让「功法即机制、自由组合、自创功法」在工程上可行、可测试、可持续扩展。**

---

## 1. 引擎选型

| 项 | 决定 | 理由 |
|---|---|---|
| 引擎 | **Godot 4.7.2**（工作区根目录已有 portable exe） | 免费开源、2D 管线成熟、轻量、单人开发最顺手 |
| 语言 | **GDScript** 为主 | solo 开发迭代最快；若未来出现性能瓶颈（世界模拟/自对弈），再局部下沉 C#/C++（GDExtension） |
| 渲染 | **Compatibility**（2D 阶段） | 2D 国风手绘项目，兼容性最好；P2 若做 3D 战斗试点，一键切 **Forward+**（卡通渲染），代码零改动 |
| 目标平台 | Windows 先行 → Steam Deck / Linux | PC 优先，主机后议 |

## 2. 架构总纲：数据驱动 + 组合式

策划文档里的概念与代码的映射关系：

| 策划概念 | 工程实现 |
|---|---|
| 功法 | 自定义 `Resource`（数据声明）+ 机制脚本（核心循环），**数据与行为分离** |
| 五大交互面 | 五个子系统（singleton），各自管理自己的状态并广播事件 |
| 功法组合 | 实例化时**接口匹配检查**（读取 Resource 声明 → 合法性判定） |
| 境界权限 | 规则解锁表（境界 → 可用机制层） |
| 世界功法库 | 数据表 + 版本化（NPC 改良 = 新版本条目） |
| 自创功法 | 元件库（机制元件的标准化接口）+ 运行时拼装 + 序列化存档 |

### 2.1 六大交互面 → 六子系统

```
systems/
├── status_system.gd    # ①状态面：单位状态/标记 的添加、叠层、到期、查询
├── resource_system.gd  # ②资源面：战斗四池（气血/体力/玄力/魂力）与寿元等 的收支与透支
├── field_system.gd     # ③场地面：地格改写（阵图/火区/雷域）、区域查询
├── unit_system.gd      # ④单位面：实体注册、召唤物/鬼仆/灵植 生命周期
├── timeline_system.gd  # ⑤时序面：ATB 行动条、冷却、延迟结算、回卷（天机演）
└── body_system.gd      # ⑥部位面：部位结构/部位状态机、失血结算、要害判定
```

- 功法机制**只能**通过这六个子系统的 API 读写战斗状态——接口语言在代码层面强制执行（组合合法性的技术保障）
- 每个子系统用 Godot `Signal` 广播事件（`status_changed`、`field_rewritten`……），功法之间**不直接互相调用**，通过事件解耦

### 2.2 功法的代码形态

```
功法 = Resource(声明) + Node(机制)
- 声明（数据）：产出/消耗/接口/冲突/境界要求/寿元成本（见《功法系统》§2）
- 机制（代码）：一个继承 MechanismNode 的节点，挂载战斗实例上，
  订阅/广播五子系统事件，实现自己的核心循环
```

好处：
- **组合 = 实例化**：主修机制节点 + 辅修机制节点挂在同一战斗实例，接口检查在挂载时做
- **自创功法 = 元件拼装 + 新机制节点**：L2 推演改参数，L3 立道拼元件库（每个元件 = 一段可组合的小机制脚本 + 数据声明）
- **mod 友好**：功法全是资源+脚本，未来开 mod 只需要暴露声明格式
- **测试**：每个功法可单独进「沙盒战场」单测，五子系统可 mock

### 2.3 确定性战斗模拟（平衡与测试的根基）

- 战斗逻辑**不依赖帧**：回合结算、随机数（固定种子）、寻路全部确定性——速度对抗 + 规则对抗的双维命中判定同样纳入确定性内核
- 后果：战斗可**回放**（存档 = 操作序列 + 种子）、可**模拟**（AI 对手自对弈批量跑，检测无解组合/死循环/平衡崩坏）
- 战斗内核与表现层分离：内核纯逻辑（可 headless 跑），表现层只播放结果——UI 改版不影响逻辑

## 3. 存档方案

- 世界状态 + 角色状态 + 世界功法库 → JSON（Godot `Resource` 序列化或自定义 JSON）
- **版本迁移**：存档带版本号，升级时走迁移函数（修仙游戏要 EA 多年，存档兼容是生命线）
- 战斗回放独立存档（操作序列 + 种子）

## 4. 工程目录（godot/ 下）

```
godot/
├── project.godot
├── scenes/          # 场景：战斗/大地图/门派/UI
├── scripts/         # 通用代码
├── resources/       # 数据资源：功法/种族/元件/事件 的 .tres
├── systems/         # 五子系统 + 事件总线（见 2.1）
├── mechanics/       # 功法机制节点（每门功法一个目录）
├── ui/              # 界面与主题
├── assets/          # 美术/音频导入产物
└── tests/           # GUT 自动化测试（五子系统、功法单测、接口匹配检查）
```

## 5.5 美术管线（AI 辅助）

- 视觉路线：2D 国风水墨手绘（渐进混合，P2 试点 3D 卡通渲染）——见 [docs/06_美术与音效/视觉风格指南.md](../06_美术与音效/视觉风格指南.md)
- 管线：ComfyUI 概念/铺量 → 人工精修 → 关键内容外包；AI 产物提示词留档 `art/ai_generated/`（Steam AI 披露政策）
- 工程侧：表现层与内核分离（已有），美术替换不碰战斗逻辑；战场精灵/立绘按规格进 `godot/assets/`

## 6. 性能预期与风险

- 回合制 2D：渲染无压力；性能风险在**世界模拟**（NPC 人生/功法生态）——P2 再处理（分帧模拟/简化模型），P0/P1 不做
- 最大技术风险是**组合系统复杂度失控**——对策：接口匹配规则在代码层强制、共鸣表人工精选、GUT 测试守住
- 自创功法元件库是长期工程：P0 只做 3 个元件验证可行性，绝不一上来建完整元件库

## 7. 开发工作流（策划 ↔ 工程）

1. 策划文档（本 docs/）定机制 → 2. 写功法声明（Resource 数据）→ 3. 写机制脚本 + GUT 单测 → 4. 沙盒战场手测 → 5. 模拟自对弈查平衡 → 6. 回放给策划看效果
- 每次加新功法 = 走完一遍此流程；**任何阶段发现机制不好玩，回炉策划文档**
